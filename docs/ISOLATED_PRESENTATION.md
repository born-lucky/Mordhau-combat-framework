# Isolated combat framework presentation

The public-facing fork owns its interface and presentation. The main rewrite remains separate.

- The runtime and launcher default to `TestLevel`. `--menu` opens the authored Steel Lab front end with the test world loaded, rather than opening the original game front end.
- Escape, Enter and the authored resume/perspective/tools/exit buttons belong to the framework. Hidden original UI roots never draw and their VM receives neither native nor synthetic UI input in this host. Gameplay HUD events remain available.
- Health and stamina use the controlled fighter's live values and bounds. Preset strike/stab bindings are included in the controls legend.
- Palms, finger links, joint spheres and fingertip pads are authored procedural geometry driven by the existing hand skeleton. Each character currently has two palms, 30 finger joints, 20 links and ten terminal pads. There is no separate animation clock. This is a training figure, not a finished anatomical character mesh.
- The authored sword is one fixed physical assembly in the native held component frame. Its guard/blade width follows weapon-local UE Y; its long axis follows the normal trace sockets. Grip changes move the existing native held component and hand pose without rebuilding the model around the active hand grip or alternate trace. The full handle uses `GripEnd` where available. For sword skeletons without it, the authored handle is centred on the native `Part3` anchor; this inferred span is labelled separately from native geometry. Gameplay hitboxes, trace endpoints, animation timing and attack selection are unchanged.
- The default writable settings directory is `%LOCALAPPDATA%/MordhauCombatFramework/Saved/Config/WindowsClient`, independent of the main rewrite. On first use, existing original-game `Input.ini` bindings are copied into an absent framework file. Existing framework preferences and explicit input/config overrides are preserved. Original settings are never written.

## Parry-side investigation

The isolated fork previously launched with a fresh config directory and read pak defaults rather than the user's saved bindings/sensitivity. The new local import removes that mismatch. This is not proof that it explains every reported difference in parry feel.

Native `AMordhauPlayerController::GetAnglingVector` (RVA `0x15d54a0`) and `UMotionSystemComponent::RequestParry` (`0x14d1590`, machine-code branch `0x1414d1685..0x1414d16b1`) select the left block from negative angling X. `FlushPendingAnglingInputs` (`0x15d4880`) replaces X on sign reversal. No new movement-distance threshold or sensitivity multiplier has been added. Action-before-axis ordering is retained. A regression test checks a one-count reversal after a large opposite movement at both saved and pak sensitivities, including X inversion. A separate buffered-parry defect was then reproduced: re-pressing left during an active parry set the buffer, but its successful retry always became right. The owning player's freshly flushed angling X now travels through the runtime and sim into that retry, so it reselects the current side. The initial press retains its original pre-axis ordering. AI/script-only fighters have no player angling sample and retain the regular retry behavior. No timing or sensitivity threshold changes.

The core integration test `buffered_player_parry_reselects_current_mouse_side_after_cooldown` failed before the retry change (expected left, got right), then passed. It exercises an actual parry cooldown and buffered retry for left remaining left, switching to right, switching to left, and no player controller. It requires a locally generated records JSON via `MORDHAU_PARRY_TEST_SPEC`; no fixture is published. Original-game interactive side-by-side feel remains to be judged by the user.

## Weapon-frame correction, 2026-10-09

The earlier zero handle-centre error was an insufficient acceptance criterion. It checked the hand's active grip point while ignoring blade roll and the physical handle span. The custom guard was built across UE X instead of UE Y, and the short handle/guard were rebuilt around the active collision trace. In half-sword mode this moved the hilt onto the blade. The original native attachment transform was not the defect in this pass.

The existing native `ComputeGrippedTransform` reconstruction (RVA `0x14b70f0`) and grip proof/tests establish the weapon frame: guard width is UE Y, blade length is UE Z, and the attachment subtracts the active `GripLocationLocal`. After the UE-to-Bevy conversion these axes are Bevy Z and Y respectively. The authored model must occupy that fixed local frame; it must not treat the active grip as the physical handle centre. No extra camera, roll or animation offsets were added.

The replacement blade now has an authored diamond section, bevels and a pointed tip, with a fixed guard, full handle and pommel. Polearm, spear, axe and hammer families use separate authored shaft/head parts rather than the former universal sword. Unsupported classes or missing frame metadata are explicitly warned and do not receive an invented sword. These remain training silhouettes, not original weapon artwork or complete equipment coverage.

The first additional longsword render exposed a missing-`GripEnd` assumption and drew no replacement. Its native skeleton supplies a `Part3` handle anchor instead. The authored handle now reflects that anchor about the guard to define its bottom; this is an authored dimension inferred from a native socket, not a recovered original mesh boundary. The failed capture is part of the investigation and is superseded by the final acceptance run.

Short axe/mace skeletons also omit a rear socket. Those authored shafts extend 18 cm behind the fixed normal trace base, labelled as an authored rear extension. Axe head placement follows the side indicated by native `StickyPoint` or additional trace sockets. These choices preserve the native attachment and hand poses without claiming that the new silhouette reproduces original mesh dimensions.

The actual war-axe render caught another classifier error: its `TwoHandedSword` folder is an animation family, not its physical weapon type. Silhouettes now use the equipment class name alone. A regression check covers axes and maces inside the sword directory. Equipment identity and drawn part types are both required by acceptance, so a correctly attached but sword-shaped axe cannot pass.

Verification checks the actual rendered part transforms converted back into weapon-local space, guard-axis agreement and full handle endpoints across first person, third person and alternate grip. Private evidence lives under ignored `build/weapon-frame-pass/`. Unit checks cover the native width axis, handle span, rigid assembly under attachment changes, missing-socket handling and invalid segments. Visual inspection remains necessary: a passing centre-position metric alone cannot establish correct blade roll, hand contact or complete vanilla animation parity. All vertex arrays in this change are authored; no original mesh vertices, extracted JSON, captures or cache files are committed.

Final acceptance used compiled source `e4e564d3d425d0135c59ea70c8a2c2ca0c921657` and runtime SHA-256 `4d1a47e60b2ad1296ca9fcce58eef3067a10c8f74317047bfb5d5d4194e7b01f`. All six internal runs exited successfully and produced fresh PNG/JSON captures from that same executable: greatsword, longsword, zweihander, halberd, war axe and mace. Thirty sampled poses passed the fixed-frame checks; each stab sample was confirmed as native release stage 1. Available alternate modes switched successfully. Sword endpoint error was below 0.1 mm and part-local matrices stayed invariant within the stated tolerance across pose/grip/view changes. Six visual-frame, 17 input and three framework-menu checks passed. These checks establish this authored presentation pass, not complete original-game parity or every equipment class.

Screenshot writes are asynchronous. The harness waits after its final capture and requires all PNG/JSON modification times to follow process start; existing images cannot satisfy a new run. The source-only private package audit passed for 623 tracked files. The main rewrite executable retained SHA-256 `7CBAC0EB98D30FAB88A14D72227D3C509A943199904E5624FAD9FB07DDA23F02`.

## First-person lower-body correction

The authored figure incorrectly treated every non-arm part as third-person only. Native `CreateFPMeshIfNone` (RVA `0x14b8d30`) excludes head and torso from the merged first-person mesh; it retains legs and feet. The authored mask now keeps the pelvis, thighs, calves and feet visible in first person, while hiding the head and torso there. Foot shapes follow the existing `Foot` to `ToeBase` joints. The native camera/animation pipeline and capsule shadow proxies are unchanged; these visible first-person parts remain non-shadow-casters. Private look-down/locomotion captures are recorded under ignored `build/first-person-legs/`.

The final lower-body run exited successfully with fresh captures: seven authored lower-body parts were visible in standing/walking first person, zero head/torso parts were visible there, and all four head/torso parts returned in third person. The look-down PNGs were inspected. The weapon-frame regression checks passed. Runtime SHA-256 `938f335642465b0a08460dfd10f59fd0c9f72ea0f5ced8269c60fd86765e20b4`.
